# Moje finanse v1.4.2

The administrator dashboard has one Moje finanse tile. app/finances.js opens four tabs: earnings, payments, routes and cash. The private vault iframe at /app/priv/index.html?finance=1 uses the existing payment PIN/password (minimum six characters) as the shared UI gate. Direct legacy private URLs redirect to /app/?finances=1. Switching tabs preserves drafts and does not reload the main app.

Payment and cash content stays encrypted with AES-GCM / PBKDF2-SHA256, 600,000 iterations, random 16-byte salt and fresh 12-byte IV. The key and password stay only in the private iframe. Parent unlock/lock/activity notifications are checked against both the frame WindowProxy and exact origin. Earnings retain their existing admin-only database tables and automatic wash-record integration; they are not converted to vault ciphertext. Their existing PIN gate is replaced by the shared payment-password UI gate. The browser gate complements existing Auth/RLS; it is not an additional server-side earnings authorization policy. Route drafts exist only in memory and are cleared on lock.

One inactivity clock covers the whole finance window: ten minutes active, one minute with the browser page hidden. Activity is shared between the parent and private iframe without sharing secrets. Explicit lock, logout, pagehide and closing clear earnings, route data, cash DOM and vault keys. Late earnings/route replies cannot recreate a locked pane. The previous main-app screen remains intact.

Data persists per administrator across devices in `cf_payment_vaults`. Save RPC uses optimistic revision checks. No silent overwriting of a newer device's state. Own encrypted backup/restore and PIN change in Settings. Ten-minute inactivity lock, one minute when hidden, immediate pagehide lock. No unencrypted browser storage, PDF upload, paid AI or automatic bank access. Client-loaded PDF.js 4.4.168 parses text PDFs; scanned PDFs and individual transfer confirmations are unsupported.

Import flow: first import shows only unique contractor names with enabled checkboxes. Amount recognition does not gate contractor selection. Names and expected amounts are edited in a second stage, which saves only payments matching the resulting rules. Further imports update only tracked contractors; Edit list > import adds new contractors, including from previously imported files. Complete coverage requires explicit confirmation and no unread amounts. Overlapping statements retain real repeated transfers without duplicating re-imported occurrences. Source text is retained only for saved payments, inside encrypted state; PDFs and PDF passwords are not stored.

Recognition uses exact destination account, or normalized contractor identity when account is absent, with optional title fragment and exact currency. Conflicts stay unassigned. History permits manual assignment, ignored transactions and month overrides, saved immediately. Rule names never serve as payment identity. Deleted rules leave transactions intact. Unknown coverage produces “Brak potwierdzenia”; full coverage after the deadline produces “Brak płatności”. Monthly sums and differences use integer cents and never mix currencies. Not a legal/tax obligation calculator.

Limit: the parser has been verified against the supplied mBank statement layout; other export formats may need adaptation. Missing parsed amounts are reported. Unsupported layouts must be corrected or supplied for parser adaptation; successful fixture tests alone do not establish compatibility with every bank PDF. Full-period confirmation is an explicit user assertion, not inferred from the filename.

Checks: `node --test tests/private-payments.test.cjs`; database rollback integration: `supabase/tests/private_payment_vault.sql`. DOM integration checks with mocked Auth/database cover encrypted persistence, PIN creation, wrong PIN, editing, lock and PIN change. No real administrator session is used in those tests. Chromium download was unavailable, so visual browser verification remains pending.

Password-protected PDFs use PDF.js onPassword with a local dialog, incorrect-password retry and cancellation. Password exists only during worker decryption, is cleared from the form and is not saved or sent to the database. Plain PDFs do not prompt.

Password checks: `node --test tests/private-payments-password.test.cjs`. Additionally tested the actual PDF.js 4.4.168 reader against a generated encrypted text PDF: incorrect/correct passwords, extraction, cancellation and plaintext import. The supplied four-page mBank statement was locally decrypted and checked with the actual PDF.js reader: 56 outgoing operations, no unread amounts, and the debit total agrees with the bank summary. No bank contents or password were committed.

Contractor preview v1.0.11: names only, no editable fields, transaction descriptions, amounts or dates. Card references and masked card numbers do not create duplicate contractors. The parser reads the debit column separately from balance, joins same-column booking-date details and keeps bank account currency for foreign card purchases. Actual-statement DOM tests covered 22 unique selectable contractors, tracked-only history, adding new contractors from the same file, and duplicate-free re-imports.

Adding contractors after list editing uses an explicit visible file input in a separate upload step. The native picker is no longer invoked after awaiting encryption/database persistence, preserving compatibility with browsers that require a direct user gesture. Cancelling file selection keeps the upload step open.

Similar-name suggestions during contractor selection are same-currency only. The user explicitly chooses a new rule or linking the new recipient alias to an existing rule. Existing settings remain intact. Alias recognition survives rule-name editing and applies to later history imports; manually editing the recognition recipient resets its aliases. Saved-rule merging preserves transactions/imports and rewires assignments to retained IDs.

The main toolbar offers manual merging: select at least two rules, choose the retained rule name/settings, and save with one merge button. The union of controlled intervals and all histories/recipient variants are retained. Currency, month allocation and title filter must agree; incompatible rules are rejected before mutation. Import disables merging while PDFs are being read. Bank-account/card merges retain both identity types.

Above the watched list, the current-month schedule shows rule names and expected payment deadlines, sorted by date. It follows Warsaw current date independently of the selected history year, respects active control periods/month offsets and clamps deadlines to the last day of shorter months. Locking clears the schedule names from the DOM.

Cash ledger v1.0.12: positive PLN grosze, income/expense direction, short description, creation date and deletion. Cash is included in the same encrypted vault, PIN change and backups. Legacy vaults without a cash property initialize an empty ledger. All-time balance is independent of bank payment totals and year selection. Only the list scrolls, keeping entry controls and balance visible.

Unified-window checks: node --test tests/private-payments*.cjs tests/private-payments-cash.test.mjs tests/dojazdy.test.cjs. Browser integration: node tests/finances.browser.cjs (Playwright Chromium installed; optional CF_CHROMIUM_EXECUTABLE and CF_CHROMIUM_ARGS JSON). It uses mocked Auth/database, real vault encryption, actual earnings renderer and calculator, with phone/tablet/desktop layouts. No real user data or PIN is used.

Statement import now offers an optional PDF password alongside file selection. A batch may share that password; files with a different password prompt separately. The input is cleared before reading, plaintext files remain supported, and passwords are not included in imports, saved transactions or encrypted vault state.

Bank income v1.2.0: the parser returns positive operation amounts separately from tracked outgoing payments, never account balances. All bank credits (including refunds and own-account transfers) are encrypted as `incomes` in the existing vault; no schema or RLS changes. The payments tab displays monthly/year totals per currency, full completed-month average, credit details and persistent exclusions. Full months with no credits count as zero; missing, partial, ongoing and legacy unparsed months are excluded from the average. Existing statements have to be uploaded again because earlier versions discarded credits and never retained PDFs. Income coverage requires a re-read (`incomeVersion:1`), matching account currency and explicit full-statement confirmation. File/range metadata alone cannot retroactively prove credit coverage. Re-imports preserve exclusions and real same-day repeats, deduplicate overlapping statements and keep watched-payment history intact. Backup/restore, PIN changes and lock cover credits too. Tests: `node --test tests/private-payments-income.test.cjs`.

Import review v1.2.1: amount errors, missing ranges and operations outside the statement range are listed per file in expandable details. They disable full-period confirmation but do not block saving recognized operations in the batch. Invalid files cannot inherit an earlier full-period flag. They remain incomplete for averages and missing-payment checks until corrected.

Account access v1.3.0: owner/admin Auth/RLS replaces the additional finance PIN. Existing vaults convert without changing rule, transaction, income, import or cash arrays. An `accountKey` alongside the envelope provides automatic opening; it is not an additional secret against an authorized database reader. PIN change controls and extra inactivity locks are removed. Legacy backup decryption remains available with the historical backup password.

Income tab v1.4.0: separate fifth “Wpływy” tab, all existing credits moved out of payments. Salary section “Wynagrodzenie z umowy spółki” groups actual incoming booking dates by month, matches normalized titles (wynagrodz*, wynagr., pensj*, wypłata), and includes internal and BLIK credits. Automatic title matches are suggestions, not proof of the legal basis of a transfer. Each credit has an optional boolean salary override (Yes/No/Automatic), independent of the general total exclusion. Overrides persist in the existing encrypted vault and survive re-import, account reopening and backups. Monthly salary average uses the same per-currency, confirmed full completed-month coverage as all income, including zero salary months and excluding ongoing/partial/missing months. No schema migration or real bank data changes. Checks: private-payments-income and private-payments-salary unit tests; finances-income.browser.cjs uses mocked account/database and actual encryption across desktop/tablet/phone.

Company income v1.4.1: “Wszystkie wpływy na konto” sums only statements designated m/mBiznes in their filenames. E/eKonto and unknown sources are excluded from totals, monthly details, completeness, average denominator and the legacy backfill notice. Import hash resolves the authoritative source name, falling back to the credit source filename when no import metadata is available. The salary section and stored/imported data are unchanged. Tests include mixed m/E statements, private-only coverage, unknown sources and exact totals/details in the browser.

Cached return v1.4.2: a persisted pagehide preserves the account-mode private frame only when hosted by Pack. Legacy PIN mode, standalone pages and non-persisted departure still clear keys. Pack/module pageshow rechecks owner/admin access before revealing cached content. Explicit close/signout always lock. Workspace recovery stores tab identifiers only, not bank data or unsaved forms.


## Automatic bank statements v1.5.0

`pack-bank-mail` uses the existing encrypted o2 credentials and exact mBank sender/subject filters. Private originals are stored in `pack-bank-statements`; only the authenticated owner/admin can request a one-minute download link. Separate server-only settings store an encrypted optional PDF password (HKDF/AES-GCM, no password returned to the browser). Settings and file metadata are not directly exposed to authenticated/anonymous REST clients.

The daily job runs at 06:15 UTC from the seventh through month end, fetching statements received in the current month and importing the previous statement month. Initial activation starts with the next seventh. Delayed arrivals and pending imports retry; already imported message parts are skipped. Content hashes and the existing reconciliation engine also deduplicate manual imports and repeated attachments while retaining real repeated transactions and user overrides. At most eight files per invocation; remaining files retry. Encrypted/unsupported documents stay available with an actionable error. PDFs are parsed using pinned PDF.js on the server, not sent to an AI API. Vault writes compare revisions and retry conflicts; completeness is never inferred or silently confirmed.

Tests: bank import/date/reconciliation unit tests; actual deployed password-protected synthetic PDF parsed successfully (one debit, one credit, correct range); read-only mailbox probe found attachments in the saved folder. Real bank-file import awaits a PDF password configured in Moje finanse → Automatyzacja. Reminder worker v4 was deployed after explicit approval for its existing OpenAI PDF-reading flow. It checks once per Warsaw day from the start of the billing month through the due day; applied invoices stop further checks for that occurrence. The daily schedule runs at 06:00 UTC.
