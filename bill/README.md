# Bill 1.0.15

Admin-only invoicing at `/bill/`. Uses the existing CleanFleet Supabase login, with a separate browser session key. No signup and no direct browser access to billing tables. The server checks the current user and administrator role for every operation.

Both brands share seller NIP 6351861297 and an atomic monthly `A[n]/MM/YYYY` counter. October 2026 starts after A2. Logos are chosen by `?brand=cleanfleet` / `?brand=robisie`, and can be changed before issue. `?new=1` opens a new draft. Robisię may add `&source=<investment UUID>` to prefill investor details. Source applications are read only: Bill does not mark work paid or change their ledgers.

The first version handles ordinary domestic VAT-exempt sales invoices in PLN/EUR, buyer/optional separate recipient, payment details, notes, and browser Print/Save PDF with the selected logo. Invoice positions and amounts are reviewed in Bill. Installment invoices, advance/final invoice settlement, corrections, foreign buyer identifiers and offline24/certificate signing are not implemented in this version. The issue date for online submission must be the current Polish date. Purchase-invoice import is deferred as requested.

## Backend

Apply `supabase/bill-schema.sql` once. Deploy `supabase/functions/cleanfleet-bill/index.ts`, `invoice.js`, `ksef.js`, and its dependency `../cleanfleet-ksef/core.js`. Keep JWT verification enabled. The `invoice.js` copy must stay identical to `bill/core.js` (covered by a test). Existing KSeF download code is unchanged.

The saved production KSeF token is decrypted only on the server with the existing domain-separated credential codec. KSeF access remains scoped to the signed-in administrator's stored configuration. Real submission occurs only after the user chooses “Wyślij do KSeF” in a separate confirmation for an already issued invoice. Acceptance is polled separately, then the KSeF number, signed UPO and original XML are available. An interrupted send is reconciled against the original KSeF session and plaintext hash; it is never automatically reposted. Accepted invoices cannot be edited or deleted.

PDF QR codes are generated from the SHA-256 of the exact stored XML and the issue date, only after confirmed KSeF acceptance. Drafts and unconfirmed documents have prominent preview labels; offline certificate QR codes are not fabricated.

## Counterparties (1.0.3)

The invoice buyer, optional recipient and contractor book explicitly distinguish a private person from a company. Legacy records infer the kind from their NIP. A company requires a valid Polish NIP; a private person uses `BrakID` in FA(3). Email and phone are optional, with optional REGON/KRS for companies. These extra details are retained in the contractor book and invoice payload; the invoice presentation contains standard invoicing identity.

The admin-only `lookup-nip` action fetches the official MF VAT register at `https://wykazpodatnikowvat.mf.gov.pl/api/search/nip/{nip}?date={YYYY-MM-DD}` (the production address effective 15 October 2026). It does not use or claim to use GUS/BIR. Only invoicing identity is returned, with no PESEL, representatives or bank accounts. Successful responses are cached for six hours per NIP and Polish date in each isolate, with a 200-entry bound. Unavailable or absent records preserve manual entry. Lookup does not save a contractor or issue an invoice.

## GUS / REGON (1.0.4)
Production BIR1 lookup uses an administrator-provided GUS production key (Settings). Key is verified by login, encrypted with a dedicated codec and stored only in service-role-only bill_settings. Bootstrap returns only bank and gusConfigured. Settings patches are atomic and cannot erase the other setting. No test credentials are accepted in production. GUS is attempted first, MF is a fallback; returned source and fallback warning are shown. No registry result is automatically saved or issued as an invoice.
GUS access is free but requires a key from https://api.stat.gov.pl/Home/RegonApi?lang=pl. KSeF credentials do not grant GUS access. No production lookup without the user's key has been verified.

## German TVM buyer (1.0.5)
Party country PL/DE is retained in forms and XML. German company identifiers use DE + nine digits, serialized as KodUE=DE and NrVatUE without prefix; Polish NIP validation stays unchanged. Invoice VAT treatment is unchanged.

## KSeF browser (1.0.6)
The KSeF tab reads production sales (Subject1) and purchases (Subject2), including invoices issued outside Bill. Default Polish calendar month; custom inclusive dates up to 99 days; date basis Issue / Invoicing / PermanentStorage. Lists use metadata pages of 250 with explicit load-more/truncation notices. Search and client sorting apply to loaded rows.
Single PDF retrieves original XML bytes, verifies metadata SHA-256 and renders with the existing pinned CIRF renderer. Bulk PDF uses an asynchronous encrypted KSeF export rather than repeated single-download calls; encrypted/clear part sizes and SHA-256 are checked, then every selected XML is checked against metadata. ZIP contains only selected PDF files, named by unique KSeF numbers. Maximum 250 selected files, 100 MB compressed export, 150 MB extracted XML/PDF output. Cancel stops client requests/conversion and no partial ZIP is offered.
Saved production KSeF credentials stay server-side. Short-lived encrypted browse/export/part tickets bind access to the authenticated admin user. XML and download URLs are kept only in current-page memory and cleared on logout; no invoice/finance records are modified. Single XML memory cache: 20 MB / 32 invoices. PDF overlay includes close, download and open-in-new-tab for mobile PDF readers. Shared CleanFleet renderer/ZIP assets are reused without modifying them.
Validation: Bill/crypto/UI tests, actual CIRF PDF generation with visual inspection. Production authenticated read still needs verification with the user's session; no credentials or user session are manufactured for this check.

## Corrections and registry identity (1.0.7)
Accepted Bill invoices have a correction action. A new draft has a dedicated immutable parent/reference and server-generated before snapshot. The original row/XML is never changed. Data mode corrects buyer name/address with zero financial delta. Amount mode edits final positive/zero line values; FA3 contains before rows (StanPrzed=1), after rows and the signed difference in P_13_7/P_15. Buyer tax identifier, currency, recipient and service date remain fixed. Correcting a wrong buyer NIP requires zeroing and a new original invoice.
Corrections use the existing shared A/month counter and standard explicit issue/send confirmation; draft creation allocates no number and sends nothing. A service-only unique index permits one non-rejected correction per parent. Reopening the parent returns its existing correction; successive corrections are created from the accepted correction and refer to the root and previous document. Server rebuilds references/before state on save/send. This supports corrections to accepted invoices stored in Bill; importing originals issued outside Bill for correction is not implemented.
A reported missing trade name was traced to MF returning only the proprietor name while no GUS key was configured. No name was removed by PDF or XML generation. Source labels now explicitly distinguish MF-only from enabled GUS and warn about missing trade names. For enabled GUS, F/SilosID1 uses a full BIR12 CEIDG report name, checked against REGON; unavailable full report leaves a visible manual-name warning. The issued invoice and contractor names were not silently rewritten.
Validation: data/increase/decrease/zero correction XML against the official FA3 XSD; immutable-reference, zero-delta, chaining and GUS full-name tests; correction HTML/PDF visual check. No live correction was issued or sent.

## Correction prefix (1.0.8)
New corrections receive KA[n]/MM/YYYY and ordinary invoices A[n]/MM/YYYY from the same monthly atomic counter. Existing issued numbers are not rewritten. Editor/confirmation previews use the same prefix.

## Temporary KSeF read failures (1.0.9)
GET reads and POST invoice metadata queries retry network errors / HTTP 502,503,504 at most twice (three attempts total) with bounded backoff and short Retry-After support. Invoice submission, online session creation, auth token operations and export creation are never automatically repeated. 429 is returned with Retry-After without automatic retries. Read failures have operation-specific messages and retry metadata rather than invoice-send uncertainty text.
A failed list refresh retains the previous rows and selection and explicitly marks them potentially stale. Initial failure says the list has not been loaded; it is not presented as a successful zero-invoice result. A dedicated retry button refreshes the list. No outage-wide availability assertion is made from a single 503: public production certificates/challenge returned 200 during investigation, while unauthenticated metadata correctly returned 401; authenticated production reads remain user-session dependent.

## Accepted sales/corrections visibility (1.0.10)
Entering the invoice list refreshes Bill records; entering KSeF refreshes metadata even if the tab had already loaded. For sales filtered by issue date, the first metadata page is supplemented with matching accepted Bill invoices (including zero-value corrections), using the saved original XML hash. Remote KSeF metadata wins when the same KSeF number appears; no duplicates are shown. Local rows have an explicit Bill/accepted-in-KSeF source label. No acceptance/acquisition timestamp is invented, so this supplement is not used for other date bases or purchases.
If KSeF read fails and confirmed Bill sales are available, the response is explicitly partial and warns that sales outside Bill may be missing. PDF/ZIP for Bill-only rows use the authenticated immutable saved XML, verified by SHA-256 and matching accepted status/KSeF number, without waiting for a KSeF export. Other selected rows still use verified KSeF exports. Cancel/unmount guards prevent old operations from repopulating state after navigation/logout.

## CleanFleet vehicle invoices (1.0.11 / CleanFleet 1.56.7)
The existing attachment generator has a separate Bill mode. Selected approved Michał wash records are re-read and locked on the server, scoped to company, billing company and service month, with one currency and integer-cent total. The browser total must match. One description is entered or chosen from built-in/prior document suggestions. Bill receives one saved draft with CleanFleet logo, buyer from the billing company (or company), last wash service date, exact sum, and shared numbering on issue. The saved draft opens for review; it neither allocates a number nor posts to KSeF.
Service-only `bill_fleet_attachments` stores the immutable vehicle snapshot and selected PDF options; `bill_fleet_items` reserves each wash against another Bill draft. Draft deletion releases reservations. Issue triggers atomically add the CleanFleet receivable and invoice items with the final Bill number; duplicate issue returns the same document. Stale vehicle cost/date/company/billing/performer or an existing manual assignment blocks issue and rolls back number allocation. Payment flags and earnings are untouched. Linked CleanFleet financial fields/items cannot be silently rewritten by legacy attachment generation or backup replacement; payment status can still change. The trigger-only protection function uses a fixed empty search_path and a narrowly scoped SECURITY DEFINER read of private links, with EXECUTE revoked from all client roles.
Both applications render the same A4 PDF from the authenticated snapshot with a shared `fleet-pdf.js` renderer, embedded Polish font, repeated table headers and whole rows across pages. No dependency on the legacy attachment storage bucket. The snapshot stays persisted; PDF bytes are generated on preview/download. Bill has a separate “Wystaw fakturę” action for these linked invoices, followed by explicit KSeF sending, with no combined issue/send action. Online same-day issue-date checks remain. Vehicle attachments never enter FA(3) XML or the KSeF send body. Original invoice attachments are not relabeled as correction attachments.
Deployment: apply `supabase/bill-fleet-schema.sql`, then `supabase/bill-fleet-protection.sql`; include `fleet.js` with existing Edge dependencies. Tests: `bill-fleet.test.mjs`, Bill/KSeF regression suite and rolled-back `supabase/tests/bill-fleet.sql`. Real invoices are not issued for QA.

CleanFleet 1.56.9: explicit `includeUnassigned` opt-in permits legacy null-billing washes to be invoiced to the selected active billing company in the same currency. Other non-null billing companies stay excluded. Database drafting requires the option, issue rechecks each original snapshot billing ID rather than replacing it, and no wash/vehicle assignment is changed. Apply `bill-fleet-unassigned.sql` for existing installations and redeploy `fleet.js`.

## Separate issue and send (1.0.12)
All invoice types (both brands, ordinary sales, linked CleanFleet invoices and corrections) are issued locally first, without KSeF authentication or requests. The service-only `bill_issue_prepared` RPC freezes the server-normalized/canonical payload and allocates the monthly number in one locked transaction. Repeat requests return the same issued row. PDF/print is then available with the actual invoice number and unconfirmed KSeF label. A separate “Wyślij do KSeF” button and confirmation send the issued record; `send` rejects drafts before KSeF authentication or any numbering RPC. No UI action combines issue and send. Existing same-day online submission checks and uncertainty reconciliation stay in place. Apply `bill-issue-prepared.sql` and redeploy the Edge function. Validation includes backend/client separation tests, invoice/crypto regressions and a rolled-back service-role transaction (no real document or KSeF call).

## Immediate return (1.0.13)
Returning from invoice detail/editor (including the sidebar invoice link) renders the existing list immediately, without bootstrap requests, a save operation or the blocking work indicator. Explicit writes/status checks still refresh after completion. Successful draft saves immediately replace/insert their row in the list cache, so returning shows saved edits and new drafts. Unsaved-edit discard confirmation remains.

## One position per vehicle (1.0.14 / CleanFleet 1.56.10)
New CleanFleet vehicle drafts always use `vehicle-lines` layout. The server builds each invoice line from one selected wash: service description + registration plate, qty 1, its individual saved cost. Each price and registration suffix (not merely the total) is validated on save and again inside the issue transaction. The original snapshot remains an internal billing association/reservation, not a generated PDF attachment. The attachment action returns `noAttachment` metadata for these rows and both UIs omit attachment controls; CleanFleet PDF actions lead to the Bill invoice. All vehicles are present in the invoice PDF/FA(3) XML. Existing separate issue and send actions remain. Existing legacy documents/attachments are not rewritten. Maximum 200 selected records matches Bill's validated line limit; service description limit is 400 to leave space for plate suffixes. Apply `bill-fleet-vehicle-lines.sql`, deploy Edge dependencies, then static clients. Tests cover per-line price/plate tampering, PDF HTML/XML content, no-attachment UI and rolled-back service-role issue.

## Robisię invoice modes (1.0.15)
New project imports and stage links default to simple mode: exactly “Usługi remontowe” for project/balance choices and “Usługi remontowe — rozliczenie etapu N” for a stage, using its 1-based array position, independent of the editable stage name. Neither investment title nor contract number is added to invoice service names. Ownership checks and stage lookup are unchanged.
The optional detailed mode copies every included nonzero-quantity row from the active final calculation, including unfinished work, with names, units, displayed quantities/prices. It covers the whole final calculation, not a single stage, receipts, materials, credits or previously invoiced installments. For a stage, select the whole-project amount first to enable detailed mode. Switching is explicit and previews the full amount. Empty, negative or over-200-line calculations show a clear unavailable reason. Opening/refreshing suggestions does not overwrite a saved draft. New project imports reset the previous project's lines to a zero-valued simple line.
Discounts and imported source-settlement rounding are allocated in integer cents across source rows, preserving the exact final-calculation total. Optional signed per-line `discount` is retained through editing, normalization, PDF, correction snapshots and FA(3) P_10/P_11. PDF labels the adjustment explicitly; original unit prices remain visible. Calculation source and ledgers are read only. Fleet rows reject extra discounts in both API validation and the issue trigger. Apply `bill-fleet-no-discount.sql` and deploy `app/robisie/billing.js` plus existing dependencies with the Edge function.
Validation: mode/name/stage and cent-allocation tests, Bill and Robisię regression suites, correction preservation, official production FA(3) XSD (including a signed 1-grosz rounding case). No real invoice is issued/sent for QA.
## Ręczny status zapłaty i potwierdzenie wyciągiem (1.0.29)
Przycisk „Zapłacona” przy wystawionej fakturze zapisuje tylko ręczne oznaczenie, bez dopisywania fikcyjnej daty lub kwoty. Można je cofnąć. Oznaczenie nie zmienia faktury, KSeF, wpływów Robisię ani płatności CleanFleet. Jest przechowywane w osobnej tabeli `bill_payment_evidence`, dostępnej wyłącznie dla serwera Bill.

Przy imporcie firmowego wyciągu m/mBiznes i otwarciu Bill sprawdzane są dodatnie wpływy z zaszyfrowanego sejfu. Tylko jednoznaczny, pełny numer dokładnie jednej faktury w tytule, zgodna waluta i kwota nieprzekraczająca należności powodują zapis rzeczywistych wpłat. Kwota, data i nazwa wyciągu zastępują w widoku ręczny status; pełny tytuł i dane płatnika pozostają tylko w szyfrowanym sejfie. Sama równa kwota, prywatny wyciąg E/eKonto, wyłączony wpływ, dwa numery w tytule i nadpłata nie oznaczają automatycznie faktury. Ponowne wczytanie nie dubluje wpłat. Wcześniejsze wyciągi w trybie konta są uzgadniane przy otwarciu Bill.

Wdrożenie: najpierw migracja `20261023093000_bill_payment_evidence.sql`, potem funkcje `cleanfleet-bill` i `pack-bank-mail` wraz z modułem `_shared/bill-bank-match.js`, na końcu statyczne pliki Bill.
